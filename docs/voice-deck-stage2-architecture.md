# Этап 2: аналитика данных и осмысленные слайды

Статус: основные локальные функции этапа реализованы на `stas_last`. Проверяемая вертикаль и ограничения перечислены в [stage2-provenance-acceptance.md](stage2-provenance-acceptance.md). Реальный LLM-прогон целой колоды из браузера ещё не подтверждён.

## Цель и границы

Автор загружает один или несколько наборов данных вместе с брифом и дизайн-системой. Сервис помогает понять, что можно корректно показать, объясняет выбор и передаёт выбранные факты в генератор презентации. Итог должен оставаться проверяемым: нули, пропуски, выбросы, знаменатели, единицы и источник не теряются молча.

Модель может помочь вписать подтверждённый смысл в рассказ и выбрать выразительный заголовок. Она не рассчитывает метрики и не получает права менять числа или переименовывать новый тип графика. Тип визуализации и числовой набор рассчитываются детерминированным кодом.

```text
CSV / XLSX / JSON / TXT / Markdown
        ↓
Сохранённый DatasetBundle и исходные SHA-256
        ↓
Профиль + цель автора → AnalyticalPlan → выбранные подтверждённые факты
        ↓
ResolvedStyle → Layout → HTML / PPTX → PDF через экспортный движок
```

`AnalyticalPlan` не зависит от шаблона. Одинаковые байты и цель выбирают одинаковые поля и преобразования в разных темах. Тема влияет на оформление и композицию, но не на числа.

## Контракты

- `Dataset`: сохраняет исходный файл, имя, hash, таблицы/листы и номера строк. Для этих загрузок предел 1 МиБ на файл, 7 файлов в пакете и 21 таблица.
- `DatasetProfile`: типы и роли колонок, confidence совпадений, пропуски, кардинальность, выбросы, кандидаты метрик, категорий и временной оси. Роли — гипотезы профайлера.
- `AnalyticalGoal`: текстовая цель автора; распознаются динамика, сравнение, доли, распределение, взаимосвязь, справочник и безопасный подсчёт строк.
- `VisualizationCandidate`: до трёх вариантов с требуемыми полями, исходными/исключёнными строками, объяснением и ограничениями.
- `AnalyticalPlan`: детерминированный hash данных, цель, профиль, выбранные поля и ранжированные варианты.
- `DataProvenance`: исходный dataset id/SHA-256, content hash, поля, исходные/показанные/исключённые строки, формула, единицы, знаменатель, политика пропусков, предупреждения и номер страницы.
- `ResolvedStyle`: токены после применения выбранного приоритета бренда и шаблона. Аналитический выбор от этого не меняется.

## Профилирование и аналитические правила

Поддерживаются CSV, XLSX, JSON-массив объектов, JSON `{columns, rows}`, одна явная CSV/Markdown-таблица внутри TXT/Markdown. XLSX хранит лист и исходные номера строк; текстовый и JSON источники используют номера строк/записей.

Числовой идентификатор не становится метрикой только из-за числового формата. Ноль не считается пропуском. Временная ось принимается только если периоды разбираются однозначно. Профиль показывает размер таблицы, пропуски и IQR-выбросы. Сумма метрики не появляется автоматически: аддитивность нельзя вывести из названия колонки.

Планировщик поддерживает line, bar, column, pie, histogram, scatter, grouped column, stacked column, table и KPI-счётчик строк. Гистограмма использует Freedman–Diaconis (Sturges при нулевом IQR), до 20 корзин и сохраняет крайние наблюдения. Scatter требует два числовых поля и полные пары, но не делает вывода о причинности и не считает корреляцию. Grouped column сравнивает совместно названные факт/план поля и не складывает их. Stacked column появляется только по явной цели «накопительная/состав», при двух–пяти мерах с одной явно указанной единицей, уникальной категории и неотрицательных значениях; аддитивность остаётся решением автора и явно оговорена. Ни один вариант не заполняет пропуски нулями.

Справочник более 20 строк в пакетной генерации раскладывается страницами по 20 исходных строк. Каждая страница сохраняет собственные номера строк и подпись охвата. Предел одного результата — 60 слайдов, максимум 20 страниц справочника на одну таблицу; большие источники требуют фильтрации до генерации, вместо тихого обрезания.

## Источник стиля

Текущий PPTX-путь продолжает извлекать палитру, шрифты, кегли, поля, макеты и образцы шаблона. На странице дизайн-систем можно загрузить локальный JSON с цветовыми ролями, шрифтами, шкалой размеров и полями. Приоритет по умолчанию у брендбука; пользователь может переключить приоритет на шаблон или снять брендбук и восстановить исходные токены шаблона. Загруженные значения и hash сохраняются вместе с дизайн-системой.

JSON-формат намеренно ограничен документированной схемой токенов. Импорт PDF-гайдлайна, файла Figma и папки логотипов/примеров пока не реализован. Это не называется автоматическим извлечением брендбука.

## Путь в приложении

На главной «Раскрыть смысл данных» добавляет до семи файлов. Автор задаёт аналитическую цель, просматривает профиль и причины ранжирования, выбирает свой вариант и отмечает таблицы для включения. Поддерживаемые варианты передаются одним запросом на сервер; неподдерживаемый вариант блокирует сборку. Полученные подсказки добавляются в обычную генерацию `/decks` вместе с брифом и выбранной дизайн-системой.

Пакет и снимки таблиц сохраняются на сервере. API может вернуть пакет по `GET /insights/plan/{id}`. В интерфейсе после перезагрузки восстановление последнего пакета и локального выбора автора пока отсутствует.

## Проверка и остаточные риски

- Backend-фокусный прогон: 70 тестов пакета, provenance, графиков и брендбука прошли; предупреждения только о текущем API lifespan и Starlette test client.
- Отдельный набор графиков от Astra: 361 passed, 8 skipped, включая SVG-геометрию, native chart XML и roundtrip встроенной книги данных. Живое преобразование новых scatter/grouped/stacked типов через установленный PowerPoint/LibreOffice ещё не подтверждено.
- Frontend: 656 passed, 18 skipped; `tsc --noEmit --incremental false` и production build прошли до последней UI панели импортирования брендбука. Этот build повторён после панели и прошёл; полный vitest повторить после интеграции панели ещё требуется.
- Реальный PowerPoint → PDF/PNG проверен на временном ряду: числовая ось, USD, заголовок, источник и охват видимы. Handoff нескольких датасетов до `/decks` проверен API-тестом с подменой генератора, а не настоящим LLM-вызовом.
- Испытана загрузка двух CSV и выбор вариантов в браузере. Демо-хранилище было пустым, поэтому сборка полного LLM-слайд-дека в этой браузерной сессии не выполнялась.
- Произвольные сгруппированные паттерны и пересечение объектов шаблона с нижней полосой источника требуют отдельной проверки на пользовательских PPTX.
- Для нового брендбук-интерфейса прошли 14 API/parser тестов; после изменения UI выполнен TypeScript check и production build. Скриншот/живой браузер этой панели ещё нужно проверить на собранном приложении.
- Dark Factory Astra-провайдер ранее отвечал HTTP 403. Сложную реализацию выполнил native Astra; ограниченные фикстуры/JSON-адаптер — Luna. DF не выдаётся за успешно использованный.
