# Этап 2: аналитика данных и осмысленные слайды

Статус: архитектура и поэтапная реализация. Анализ кода выполнен на `master` `760462a2800c098ae64a6575aa612124d27cba56`; локальная реализация после этой точки не закоммичена.

## Цель

Автор загружает данные вместе с брифом и шаблоном. Сервис помогает понять, что показывают данные, зачем это важно аудитории и какой способ визуализации лучше раскрывает вывод. Он выдаёт объяснимые варианты, а после выбора собирает цельный слайд с проверяемыми цифрами, подписью источника и стилем выбранной дизайн-системы.

Это не «положить таблицу на слайд» и не генерация выводов языковой моделью. Числовые преобразования, допустимые визуализации, охват строк и происхождение каждого факта рассчитывает код. Модель может помочь распознать цель из брифа и сформулировать заголовок только из готовых подтверждённых фактов.

## Что уже есть и чего не хватает

Существующий Python `designer` умеет разбирать CSV/XLSX и картинки таблиц, находить факты динамики, долей и лидеров, запрашивать у модели формулировки на основе этих фактов, добавлять аналитические слайды в рассказ и экспортировать PPTX/PDF/HTML. Этот путь следует сохранить.

Сейчас запрос колоды связан с одним `insights_id`; отдельного профиля датасета и аналитического плана нет. JSON и текст с вложенной таблицей не поддержаны как полноценные источники. Часть таблиц без повторов или числовых колонок отклоняется. `ChartSpec` не описывает распределение, scatter и stacked-варианты. Видимый источник на слайде отсутствует: он остаётся в заметках. Дизайн-система извлекает токены из PPTX, но нет отдельного резолвера брендбука и правил конфликтов стиля.

## Архитектурные инварианты

```text
Наборы данных → Профиль + цель автора → AnalyticalPlan → ResolvedStyle + Layout → PPTX / PDF / HTML
```

`AnalyticalPlan` не получает дизайн-систему, шаблон или брендбук. Поэтому одни данные и цель дают те же выбранные столбцы, агрегацию и семантику графика в разных темах. Тема меняет внешний вид и композицию, но не вывод.

Каждый итоговый факт хранит датасет и его hash, колонки, исходные строки, фильтр/агрегацию, политику пропусков, формулу, единицы, знаменатель и охват. При срезе Top-N план явно добавляет хвост («Прочее») или объясняет, почему он не показан. Нули не считаются пропусками, пропуски и выбросы не исчезают молча.

В `ResolvedStyle` для каждого свойства хранятся значение, источник и причина выбора. Приоритет: явное переопределение автора → брендбук → шаблон → документированный fallback. При отсутствии брендбука сохраняется текущий путь шаблона.

## Основные контракты

- `Dataset`: стабильный id, исходное имя, формат, размер/hash, одна или несколько таблиц, источник строк (лист/блок и исходные номера строк).
- `DatasetProfile`: размер таблицы; тип и роль кандидаты каждой колонки с confidence; пропуски, кардинальность, ошибки разбора и выбросы; кандидаты временной оси и измерений/метрик. Это гипотезы профайлера, а не скрытые преобразования данных.
- `AnalyticalGoal`: цель из брифа, выбранный автором фокус, аудитория и ограничения.
- `VisualizationCandidate`: тип, назначение, допустимые поля и преобразования, объяснение на основании профиля и предупреждения.
- `AnalyticalPlan`: версия, входные hash, цель, факты, ranked-кандидаты, выбранная визуализация, преобразования и lineage.
- `ResolvedStyle`: разрешённые дизайн-токены и provenance каждого свойства; независим от аналитического выбора.

## Проверки безопасности смысла и качества

1. Профиль не объявляет идентификатор метрикой только потому, что он числовой; текстовые ID и последовательные ключи распознаются как вероятные категории.
2. Каждая доля показывает числитель, знаменатель, единицы и охват; округление не меняет итоговую базу.
3. Динамика явно указывает период сравнения и направление. Для процентных величин используется разница в процентных пунктах там, где это правильно.
4. Для Top-N отображается полный знаменатель и хвост либо явная подпись об исключённых строках.
5. Histogram фиксирует границы и число bins; scatter требует две числовые оси; stacked-график валиден только для совместимых серий и базы.
6. Для каждой визуализации есть контрактные тесты и экспортные тесты как минимум в PPTX и HTML; PDF проверяется через существующий экспортный путь.
7. Одни hash данных и цель на двух шаблонах дают одинаковый `AnalyticalPlan`; меняются только `ResolvedStyle` и расположение.

## Внешние зависимости и границы

Поддержка Figma не считается готовой без реально доступного API, схемы авторизации и эталонного файла. Нельзя называть изображение или вручную составленный JSON полноценным импортом `.fig`. Для MVP брендбук загружается из локальных токенов JSON и читаемых PDF-правил, со списком разобранных и пропущенных свойств.

Скринкаст — отдельный демонстрационный артефакт после готовности всей вертикали; он не заменяет тесты и проверку реального экспорта. Формулы Excel не исполняются; используются лишь сохранённые Excel значения, и если они отсутствуют, автор получает предупреждение.

## Реализовано в текущем рабочем дереве

Ветка включает разбор CSV/XLSX, JSON-массива объектов и `{columns, rows}`, текст с одной явной CSV/Markdown-таблицей, детерминированный профиль и план выбора. JSON/TXT/Markdown сохраняют исходные номера записей/строк; действующие лимиты и разбор листов XLSX сохранены. Добавлены семь синтетических сценариев. Пакетный API и панель UI показывают профиль, число пропусков, альтернативы и ограничения. Выбранный поддерживаемый вариант можно отправить в существующую генерацию колоды; сервер повторно вычисляет план по переданному файлу и не доверяет значениям из браузера. Текущие фокусные тесты смыслового анализа: 181 passed, 3 предупреждения существующих зависимостей; frontend: 652 passed, 18 skipped; `npm run build` проходит. Полный исходный прогон дизайнера до интеграции материализации: 1163 passed, 28 skipped.

Вертикаль генерации работает для ограниченного набора визуализаций, но этап не завершён: bundle не имеет долгоживущего id; для выбора файл передаётся повторно. Новые histogram/scatter/grouped-column требуют контрактов/рендеринга. Источник сохраняется в выводе/заметках, но пока не виден прямо на слайде. Импорт брендбука JSON/PDF и резолвер стилей также не реализованы. Следующие задачи: (1) сохранять dataset bundle, хэши, таблицы и план; (2) расширить контракты и согласованно реализовать новые типы в PPTX/HTML/PDF; (3) добавить видимые подписи источника/охвата и просмотр экспорта; (4) импорт локального брендбука с provenance резолвера; (5) полная приёмка на наборах и короткая демонстрация.

Загрузка в Dark Factory ограничена подтверждённым HTTP 403 у его Astra-провайдера. После двух неудачных запусков Astra через DF был использован native Astra для сложных архитектурных/профильных модулей, а Luna — для фикстур; API/UI связаны локально и проверены Sol. Это честный fallback, а не выполненный DF-прогон. Незакоммиченные пользовательские изменения сохранены и не должны включаться в релиз без отдельного просмотра.
